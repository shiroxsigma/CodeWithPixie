# CodeWithPixie 解析と改善計画

解析日: 2026-09-20。対象: このリポジトリの実装、既存テスト、ローカルの pixie_core 接続境界。
実装・フロント・AI実行／永続化を分担して調査した。実モデルの能力比較や負荷測定は未実施。

## 結論

強みは、ローカルAIによるコード変更、Note／Plan、Monaco、文書プレビュー、Mermaid編集、
承認と巻き戻しが一つの作業環境でつながっていること。すでに機能の幅は広い。
次の段階で重視するのは **編集を失わないこと、AIの結果を検証できること、操作が予測どおり動くこと**。
今回を信頼性改善の第一段階とし、製品全体の完成や実モデルの高い成功率を確認したとは扱わない。

## 構成と現状

| 層 | 主な実装 | 評価 |
| --- | --- | --- |
| 画面 | `frontend/src/components/`、Monaco | Vueによるシェル、チャット状態の型付き管理がある |
| 操作ロジック | `frontend/src/legacy/app.js` | 調査開始時4,529行。ファイル、保存、検索、会話、図の処理が集中 |
| API | `app/main.py` | 調査開始時1,496行。API、セッション管理、SSE、起動をまとめて担う |
| AI境界 | `app/engine_adapter.py`、外部 `pixie_core` | プロファイル、承認、中断、予算制御、Workset、ChangeSetを接続 |
| 永続化 | `app/code_chat.py`、`app/history.py` | JSONサイドカーとローカル履歴。耐障害性とセッションとの対応が重要 |
| 品質管理 | `tests/`、`frontend/tests/`、`.github/workflows/test.yml` | Python、Vue、ブラウザ、AWP境界のテストがある |

`frontend/tsconfig.app.json` は `checkJs: false`。現在の型チェック合格は、主要な従来JSの
非同期処理やAPI契約まで型で検証できていることを意味しない。
CIのAWPチェックアウトは特定コミットに固定されていないため、再現可能な互換性検証も今後の課題。

## 今回の修正

### 会話の作業フォルダを固定

以前の会話を残して画面の作業フォルダを切り替えると、バックアップ・変更検知・
ChangeSetを使わない巻き戻しが `config.WORKSPACE` を参照していた。
元プロジェクトの変更を見落としたり、同名ファイルがある別プロジェクトを巻き戻す経路を
追加テストで再現した。

`app/files.py` の関連関数に明示的な `workspace` 引数を追加し、`AgentSession` の
作成時に固定したパスを渡す。共有設定を書き換えて一時的に切り替える方法は使わない。
フォルダ切替の前後、ターン実行中の切替、ルート外への復元拒否を回帰テストで確認する。

### 検索を入力どおりに実行

rg経路は正規表現、Python経路と置換はリテラルという不整合があった。
`a.b`、括弧、`--help` などを両経路で文字どおり検索するよう修正。
両経路にファイルサイズ上限を適用し、除外ディレクトリの走査も抑制する。
実rgを使うテストで、絶対パスのワークスペースでは除外globが効かない問題も再現・修正した。

### 会話保存と未保存編集の保護

会話保存は、並行する2要求がどちらも成功を返したのに片方の会話だけが残ることを再現。
更新全体をRLockで直列化し、同じディレクトリの一時ファイルへ書き込んでから
flush／fsync／close／os.replaceで保存するよう修正した。書き込み途中と差し替え時の失敗、
並行保存・削除、処理中のworkspace切替を含む回帰テストを追加した。
画面では、一括置換後の強制読込と逆順に到着するファイル読込応答が未保存編集を消す経路を確認。
一括置換前に対象の未保存編集を保存し、保存に失敗したり編集中の内容が変われば中止する。
ファイル読込は要求の世代・workspaceの世代・Monacoの編集バージョンを確認してから反映する。
検索も入力変更時に古い対象を失効させ、遅い応答が置換対象を上書きしないよう修正した。
置換中の追加入力は保持し、自動保存を止めて既存の競合確認へ誘導する。自動マージは行わない。
ブラウザで保存失敗500／409、Code／Note、応答順序の逆転、処理中の入力を検証した。

## 次に取り組む課題

| 優先 | 課題と根拠 | 完了条件 |
| --- | --- | --- |
| P0 | 実行中の履歴復元・削除の排他。`main.py` の `code_chat_restore`／`api_turn_delete` が実行ターンと排他されていない | 別タブからの要求も実行中は無変更で拒否し、終了後は正常に処理できる |
| P0 | 会話保存先のセッションへの対応。`code_chat.py` の保存先は現在の画面workspace | フォルダ切替後も会話作成時のプロジェクトに保存・復元される |
| P1 | 保存失敗の可視化。`saveCodeTurn` は保存APIの例外を黙殺する | 保存中／保存済み／失敗が区別でき、再試行で重複保存しない |
| P1 | SSEの復旧と負荷上限。`_turn_stream` は無制限Queueでheartbeatとreplayがない | 低速受信時のメモリ上限を測定でき、切断後にターンの結果を照会できる |
| P1 | 型付きロジックへの移行。Vueの外でDOMと巨大な共有stateを操作 | ファイル読込・保存、検索・置換、会話保存を順に型付きサービスへ分離し、異常系テストを維持 |
| P1 | キーボード操作。ファイル／会話選択のclick中心実装とモーダルのフォーカス管理 | マウスなしで開く→編集→保存→会話切替ができ、閉じたダイアログから元の操作へ戻れる |
| P2 | 再現可能な配布。依存範囲が広く、引き継ぎ資料には旧フロントパスが残る | 対応AWP版と依存を固定したクリーン環境でセットアップ・起動・更新を検証 |

バックエンドの保存ロックは単一プロセスを対象とする。複数サーバプロセスや外部アプリから
同じJSONを書き換える運用を必要とする場合は、SQLiteなどのトランザクションを検討する。

## AIを強くするための評価計画

「強いモデルへ変更」だけでは改善の判定ができない。まず以下の固定課題を合計20件程度用意し、
隔離した作業フォルダで各3回実行する。これらは提案であり、今回測定した値ではない。

| 課題 | 成功を判定する方法 |
| --- | --- |
| 既存コードの読解 | 対象ファイルと根拠が正しく、存在しない機能を説明しない |
| 小さなバグ修正 | 事前に失敗するテストが修正後に通り、既存テストも維持 |
| 複数ファイル変更 | API・呼び出し側・テストの整合性が取れる |
| Note／Plan | 読み取り専用制約を守り、指定した出力を作る |
| 承認却下・中断・上限 | 書き込みや実行が意図どおり止まり、結果が識別できる |
| 作業の復元 | 会話・作業対象・変更内容の対応が保たれる |

記録するもの: モデルID、モデル設定、CWP／AWPの版、成功率、不要変更率、制限到達率、
初回表示時間、完了時間、LLM／ツール呼出数。既存の `turn_metrics` を起点にする。
初回測定を基準として改善目標を決める。実モデルの応答品質は今回の実装テストとは別に検証が必要。

## 実装順序

1. データ保護: 今回の修正、履歴操作の排他、保存先のセッション対応。
2. AIの完遂品質: 固定課題と結果記録、失敗分類、変更後の検証と結果表示。
3. 日常の操作体験: ファイル検索、差分確認、承認、履歴復元、キーボード操作を一貫させる。
4. 拡張しやすい構造: 動作を保ちながら従来JSと巨大APIファイルを機能単位へ分割する。
5. 配布品質: 依存と互換性の固定、初回セットアップ診断、更新手順を検証する。
